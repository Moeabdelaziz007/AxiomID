# Agent Control Center — axiomid.app Landing Redesign

## 1. Vision

**axiomid.app is NOT a landing page. It is an Agent Control Center — an operating system, not a marketing website.**

When a visitor arrives, they enter a sovereign machine. The page behaves like an OS: a boot sequence, an intent prompt (not a hero headline), live system state, running agents, memory, an execution timeline, proofs, economy, and an explorer. Every number on the screen is real — pulled from live API endpoints — or explicitly labeled `simulated`. No fake green states. No invented stats. (Muraqabah: the numbers shown are the numbers the API returns, nothing more.)

## 3. Section 1 — Intent Compiler (NOT a prompt box)

The Intent section is a **compiler pipeline**, not an input field. It shows the transformation:

```
Book flight
    │  parse
    ▼
Local Intent: book flight to Cairo
    │  plan
    ▼
Capability Matching: [spend-request] [pi-payment] [agent deploy]
    │  loop
    ▼
Execution: → approved by human → executed
```

- Accepts free text + voice (Web Speech API) in the top input.
- Runs a **local, deterministic intent classifier** (no LLM dependency): keyword map → capability match.
- If no capability matches: renders `[intent:unmapped]` honestly with a suggestion to try known verbs (claim, deploy, pay, verify, explore).
- Each matched capability links to its real route (`/claim`, `/dashboard`, `/explorer`, `/docs`).
- Honesty rule: the compiler executes nothing on the landing — it *proposes* the chain. Execution happens only after explicit user action (route navigation). The word "execute" in the chain is aspirational UX showing the path, never a fake success state.

## 4. Section 6 — Execution Timeline (Executable Specification, not a visualization)

`SpecStream.tsx` is a real execution stream, not an animation of made-up steps:

```
Spec ──► Runtime ──► Execution ──► Proof ──► Replay
```

- The "spec" is a fixed script of live calls: `GET /api/status` → `GET /api/explorer` → `GET /api/did-document`.
- Each step executes a REAL fetch; the step line shows the actual HTTP result (`200 OK`, `{...}` payload summary).
- A step that fails shows `✗ <error>` — the failure is rendered, not hidden. That is the honest proof.
- Steps are sequential, one at a time, each awaiting the previous (no fake parallelism).
- Replay button re-runs the same script (loop icon).
- No fake timestamps; timestamps come from the API response (`timestamp` field in `/api/status`).

## 10. Honesty & Muraqabah constraints

- Every number comes from a live fetch. If an endpoint returns zero/empty (e.g. `averageTrustScore: 0`), we render `0` — we never scale or invent.
- No `simulated` values unless a section has no live source yet; those must carry the literal label `simulated`.
- Failed fetches render an error line with the HTTP status, and the section shows `OFFLINE` state — never a cached fake.
- No fake green states: green only for `res.ok` verified at render time.

## 12. Capabilities model (frames WS2, informs §3 Workspace)

Subdomains are **capabilities**, not products. They are commands of the one machine — the Agent Control Center — reachable at `*.axiomid.app`:

- `earn.axiomid.app` → capability: **earn**
- `skills.axiomid.app` → capability: **skills**
- `memory.axiomid.app` → capability: **memory**
- `mcp.axiomid.app` → capability: **mcp**
- `agdp.axiomid.app` → capability: **agdp**
- `openid.axiomid.app` → capability: **identity** (existing, live)

The Workspace grid (§3) presents these as the OS's installable/available capabilities. A capability is one-pager served by a single static app (WS2 `pai-subdomains`), hostname-switched. No subdomain is framed as a "product" — they are verbs/commands of the same terminal.
